# CMS integration audit, 16 October 2026

Scope: repository review and read-only checks of the deployed public APIs and configured Supabase project. No application fixes, production writes, authentication changes, migrations, or deployments were performed for this audit. Findings distinguish source evidence from live verification.

## Result

The public data connections respond, but the CMS is not yet a unified authoring system. A successful save in every existing editor cannot currently be assumed to update the corresponding public presentation. Drag and drop is available in parts of the legacy gallery and uploader, not consistently across the current Works experience.

## Verified checks

- Production `/api/works`, `/api/projects`, and `/api/gallery`: HTTP 200.
- Unauthenticated production `/api/admin/works`, `/api/admin/projects`, `/api/admin/gallery`, and `/api/admin/media`: HTTP 401.
- Unauthenticated dashboard: HTTP 307 to the admin sign-in page.
- Supabase service and public reads: 3 project rows, 0 content-block rows, 5 gallery rows, and 0 media-table rows. Counts alone do not establish write permissions or RLS correctness.
- No draft project exists, so isolation of a real draft could not be exercised with a read-only check.
- `portfolio-public/content/works.json`: Object not found. The public Works API is currently constructing its initial collection rather than reading a saved collection document.
- Local `ADMIN_EMAIL` is absent. Public/server Supabase credentials are configured. Supabase has one existing Auth user; no credentials or identities were changed.
- `npm run test:works`: 5 tests passed. These exercise schemas, API guards, conflict handling, and a simulated storage adapter; they do not cover the actual media-upload route or a real authenticated CMS session.
- `npm run typecheck`: passed.

## Findings

### P0: Works uploads are rejected by the media API

`components/admin/WorksManager.tsx:38` sends folder `works`. `app/api/admin/media/route.ts:133` permits only general, covers, content, and gallery. Once authenticated, a normal Works upload reaches the invalid-folder rejection. Prior simulated upload QA did not exercise this actual endpoint, so it missed the mismatch.

Recommendation: use a shared folder contract and test the complete real upload handler, not just a mocked successful upload response.

### P1: Existing case studies override CMS content

`app/work/[slug]/page.tsx` and related-project components prefer `lib/project-presentation.ts` for the three existing slugs. The narrative renders hardcoded sections instead of saved content blocks whenever that presentation exists. The live database currently has no content blocks.

Recommendation: migrate the approved existing copy into CMS records before switching the renderer to database content. Preserve the current URLs and visuals. Remove permanent source-code overrides after the migration is verified.

### P1: Works, Portfolio, and Gallery have separate sources

`lib/db/works.ts` constructs initial items from projects/gallery, then stores a standalone JSON snapshot on first save. Subsequent edits to project title, cover, slug, or publication status do not update that snapshot. New projects are not automatically included after initialization; unpublishing/deleting a project can leave a stale card linking to a missing page. Legacy gallery changes are not reliably reflected either, and bootstrap intentionally filters unchanged template records.

Recommendation: one canonical Works model with an optional project relation. Linked cards resolve project fields and publication state from that relation. Consolidate the admin entry points while preserving existing records during migration.

### P1: Publication and autosave use stale initial state

`components/admin/editor/ContentEditor.tsx:234` autosaves using `initialProject.status`. The publish toggle also computes its next state from that initial value without adopting the returned saved status. Editing after a publication change can restore the old state; repeated toggles can repeat the same operation. The manual save action explicitly saves as draft.

Recommendation: explicit current publication state, serialized saves, a private draft revision, and a separate publish action. A late autosave must not undo publication or publish unfinished changes.

### P1: A partial project update can erase content blocks

The PATCH schema permits omitted blocks. `lib/db/projects.ts:54` turns omission into an empty array, while `save_portfolio_project` deletes existing blocks before inserting the supplied array. A metadata-only API update can therefore clear a narrative.

Recommendation: distinguish omitted blocks from an explicitly empty list. Replace blocks only when requested, in a transaction, with optimistic concurrency protection.

### P1: Hidden Works are not private drafts; concurrent saves are not atomic

The Works document is stored in a public bucket and contains hidden items too. API filtering removes them from public lists but does not make the underlying document private. Revision checking performs a read followed by a separate upload, leaving a race when two sessions save simultaneously.

Recommendation: private draft storage and a published projection, with a database transaction and revision check performed atomically. Do not place private notes or confidential content in the current Works document.

### P2: Drag and drop does not match the requested workflow

Works uses a single-file picker and Up/Down controls; it has no drop area, multi-file import, or sortable drag handle. The case editor also reorders blocks with buttons. The legacy gallery has HTML drag events, but that does not establish touch support.

Recommendation: shared upload/drop components, multiple images per import, sortable Works and content blocks, touch support, and keyboard alternatives. Keep the public 3-by-2 grid and category layouts fixed unless a layout builder is separately requested.

### P2: Media management has fragmented and misleading behavior

The media API lists one folder with a limit of 50 and no pagination. Storage errors are returned as a successful response containing stock presets. No `portfolio_media` rows currently exist, and dashboard media totals are hardcoded to zero. `MediaUploader` accepts video but renders an image preview. File validation, accepted formats, previews, and folder behavior vary between editors.

Recommendation: one media library for all editors, real pagination, explicit storage errors, correct image/video previews, and asset metadata/usage tracking. Keep stock examples away from the default uploaded-assets view.

### P2: Validation and operational protections are inconsistent

Works has a defined schema and origin checks. Gallery accepts ad hoc payloads; project block JSON uses `z.record(z.any())`. Image hosts, URL schemes, media types, and renderer assumptions are not validated together. Project/gallery/media writes do not share the Works origin-check policy. Login throttling is an in-memory map and cannot be treated as a distributed rate limit on Vercel.

Recommendation: discriminated block schemas, safe URL/media rules shared with renderers, bounded payloads, consistent mutation protections, structured server errors, and durable throttling. Live database write grants/RLS still need a separate controlled verification; this audit does not claim a confirmed exploitable policy defect.

### P2: Site content outside Works is not editable through CMS

Hero, About, process, tools, contact links, and CV content are source-code content. The current admin has no settings workflow for those sections. Changes require a code deployment.

Recommendation: if whole-site CMS is desired, add a compact Site editor and a CV upload/content choice. Keep content edits independent of deployment.

## Proposed admin direction

- Works: three category tabs; thumbnails first; drag handles; short title; visibility; one Edit action.
- Edit panel: title, media, destination, and relevant case-study content. Optional fields under More settings.
- Shared Media library: drop files, select existing assets, replace media, show upload progress and concise actionable errors.
- Site settings only if the user includes whole-site content in scope.
- Remove repeated instructions and implementation explanations. Retain labels, validation, upload progress, saving/error state, and publish feedback.
- Preserve the approved public design and supplied copy throughout migration.

## Decisions requested before implementation

1. Whole-site CMS, or Works and case studies only?
2. Drag/drop uploads plus Works ordering, or also multiple-image imports and case-study block ordering?
3. Private drafts plus explicit publishing, or immediate public changes after each save?

## Implementation verification required

Use an authorized admin session to test upload, save, reload, preview, publish, unpublish, order, replace, failure/retry, and public propagation. Use isolated fixtures for destructive and conflict tests. Verify Supabase migrations and role restrictions rather than inferring them from source files. Test touch and keyboard reordering, and distinguish emulation from physical-device coverage. Do not report a complete CMS connection test from mocked API success alone.
